# RockBase Android engine — Phase 0 inspection / Phase 1 seam

- Current control plane: Express `backend/src/server.ts` mounts authenticated `/api` routes, including accounts/campaigns/posts/system. Local Mode only accepts loopback and bypasses login; Server Mode uses JWT. SQLite Prisma `SocialAccount` contains encrypted cookies and session health; no separate session table. `Post`, `ScheduledPost`, `Campaign`, `CampaignAction`, `ActivityLog` and `IdempotencyRecord` are centralized. BullMQ `automationQueue` is the existing job transport; Playwright lives in BrowserManager and posting/engagement services. Frontend `FarmView.tsx` is the browser session monitor, not a device registry. Windows Local Mode and Docker Server Mode must both start without Android SDK.
- Seam: additive `SocialAccount.executionEngine` default `chromium`, optional `homeDeviceId`, and persistent `AndroidDevice` registry. A typed resolver returns Chromium for legacy accounts. Do not route jobs to Android workers yet: reject unsupported Android execution before Playwright side effects until a later phase implements a real worker. Preserve the browser path without refactoring it.
- Device control: isolated `AndroidRuntimeService` (SDK/ADB/emulator process, boot, health, screenshot, app launch) plus `AndroidDeviceService` (DB lifecycle, single-host concurrency and status transitions). Windows-local-only API with existing auth, disabled on server/container mode. Device operations require known registered AVD names and must never spawn arbitrary commands. Persist AVD writable userdata in SDK's normal per-AVD directory; no `-wipe-data` or read-only clone flags.
- Phase 1 exact scope: Prisma migration, runtime/device service, protected operator API, minimal Android Farm UI, tooling/AVD smoke test without IG accounts, tests/build. `ANDROID_MAX_CONCURRENT` defaults to 3. Capacity is for running emulators, not number registered. No scheduler auto-start/lease, Instagram UI automation, or Chromium rewrite.
- Risks: SQLite DB migration must be additive and backed up by existing migration workflow; emulator port/serial discovery must not guess; HTTP handlers must serialize state transitions and check actual boot completion; in-memory locks protect one server process only, not cross-process/controller instances. Future phase needs durable lease and worker routing. If Android tooling is missing, report explicit validation blocker rather than fake device READY.
